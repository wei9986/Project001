# 视觉模块小白开发手册

> 使用方法：如果你要按天开发，请直接阅读第 18 节；第 1～17 节是可以按需展开的基础参考。

## 第 1～17 节：基础参考（按需阅读）

如果你正在执行 14 天计划，可以直接跳到第 18 节；下面内容用于遇到 Python、视觉、状态机、协议或安全问题时查阅。

## 1. 你现在要开发的是什么

这个项目不是单独的“摄像头识别程序”，而是一个物流机器人视觉模块的前期软件系统。它最终要完成：

```text
读取任务
-> 识别物料和工位
-> 将视觉结果交给任务状态机
-> 通过串口协议通知 STM32
-> 接收执行结果
-> 处理成功、失败、超时和安全停止
```

目前没有实机，所以现在开发的是“可以替换真实设备的模拟系统”。模拟系统通过测试图片、虚拟扫码器、内存串口和虚拟传感器验证软件逻辑。

## 5. 每次修改代码前必须做什么

修改前先保存一个基线：

```powershell
& $PYTHON -m unittest discover -s tests -v
& $PYTHON -m tools.离线评测 --output logs\before_change.json
```

## 7. 第一个练习：修改颜色参数

打开：

```text
config/颜色追踪配置.json
```

颜色配置大致包含：

```json
{
  "colors": {
    "red": {
      "ranges": []
    }
  },
  "tracking": {
    "min_area": 500,
    "confirm_frames": 3
  }
}
```

参数含义：

- `min_area`：目标最小面积，小于它的物体会被过滤。
- `confirm_frames`：连续识别多少帧后才确认目标。
- `max_lost_frames`：目标最多丢失多少帧后标记为丢失。
- `max_match_distance`：两帧目标中心允许的最大移动距离。

调参原则：

- 误检太多：提高 `min_area`，收紧颜色范围。
- 漏检明显：降低 `min_area`，放宽颜色范围。
- ID 经常变化：适当增大 `max_match_distance`。
- 目标确认太慢：减少 `confirm_frames`，但不能取消稳定确认。
- 目标闪烁：增大 `confirm_frames` 或 `max_lost_frames`。

修改后运行：

```powershell
& $PYTHON -m unittest discover -s tests -v
& $PYTHON -m tools.仿真验证 --output logs\color_parameter_test.json
```

不要一次修改五个参数。每次只改一个参数，这样才能知道哪个参数产生了影响。

## 8. 第二个练习：理解颜色检测结果

运行视觉检测时，结果会写入 JSONL 日志：

```powershell
& $PYTHON -m vision.颜色追踪 `
  --source 0 `
  --config config\颜色追踪配置.json `
  --log logs\vision.jsonl
```

当前没有摄像头时，不要用 `--source 0` 做验证，应使用离线图片或视频。每行日志通常代表一帧，重点查看：

- `frame_index`
- `targets`
- `target_id`
- `color`
- `pixel`
- `world_mm`
- `valid`
- `confidence`
- `coordinate_status`

人工判断标准：

- `valid=false` 时不能抓取。
- 没有目标时 `targets` 不能伪造旧数据。
- 没有标定文件时不能伪造 `world_mm`。
- 目标丢失后不能继续使用上一次有效坐标。

## 10. 第四个练习：理解任务状态机

文件：

```text
mission/任务计划.py
mission/任务状态机.py
```

状态机不是“自动执行一堆代码”，而是“收到事件后决定下一步动作”。

例如：

```text
收到 start
-> 输出 self_test

收到 self_test_ok
-> 进入 S1_READ_TASK
-> 输出 read_task_qr

收到 task_scanned
-> 进入 S2_FIRST_BATCH
-> 输出 load_first_material
```

开发状态机时不能直接跳状态。正确流程是：

1. 定义事件名称。
2. 定义事件需要的数据。
3. 定义允许接收该事件的状态。
4. 定义状态变化。
5. 定义输出动作。
6. 增加正常测试。
7. 增加非法事件测试。
8. 增加超时测试。

禁止出现“任何状态收到任何事件都执行”的代码。

## 11. 第五个练习：理解通信协议

文件：

```text
protocol/串口协议.py
protocol/传输通道.py
protocol/协议仿真.py
```

通信流程：

```text
状态机动作
-> MessageType
-> Frame.encode()
-> Transport.write()
-> STM32 返回 ACK
-> STM32 执行
-> STM32 返回 DONE 或 FAIL
```

模拟正常通信：

```powershell
& $PYTHON -m unittest tests.test_第二阶段流程.Stage2Tests.test_protocol_action_bridge_completes_over_memory_serial
```

模拟重试：

```powershell
& $PYTHON -m unittest tests.test_第二阶段流程.Stage2Tests.test_protocol_action_bridge_retries_when_done_is_dropped
```

初学者不要直接修改帧格式。先确认：

- 帧头是什么。
- 版本号在哪里。
- 序号如何分配。
- 长度如何计算。
- CRC 如何计算。
- ACK 和 DONE 如何匹配。
- 超时后重试几次。

## 13. 第七个练习：理解安全策略

文件：`app/安全监控.py`

安全判断应优先于普通动作。典型规则：

- 限位触发：禁止继续运动。
- ToF 小于安全距离：禁止靠近。
- 抓取未确认：禁止进入装配完成状态。
- 通信断开：停止发送普通动作。
- 坐标跳变：取消本次抓取。

验证：

```powershell
& $PYTHON -m unittest tests.test_第二阶段流程.Stage2Tests.test_safety_monitor_blocks_sensor_faults
```

安全代码中宁可拒绝动作，也不能在传感器不确定时继续动作。

## 14. 如何新增一个功能

以“增加一个新的传感器状态”为例：

1. 在 `app/虚拟设备.py` 增加模拟数据字段。
2. 在 `app/安全监控.py` 增加规则。
3. 在 `app/运行循环.py` 读取该状态。
4. 定义状态机事件或故障类型。
5. 增加正常测试。
6. 增加故障测试。
7. 增加日志字段。
8. 运行全量测试。
9. 运行离线评测。
10. 更新 README 和本手册。

不要直接把新传感器代码写进 `任务状态机.py`，否则以后很难替换真实设备。

## 15. 如何人工验证一个模块

每个模块都按照下面的表验证：

| 项目 | 要验证的问题 |
|---|---|
| 正常输入 | 正常数据能否得到正确输出 |
| 空输入 | 空帧、空字符串、空列表是否安全处理 |
| 错误输入 | 类型错误、格式错误是否被拒绝 |
| 边界输入 | 最小值、最大值、临界距离是否正确 |
| 延迟 | 超时后是否进入正确状态 |
| 重复 | 重复事件或重复数据是否不会重复执行 |
| 丢失 | 目标、Tag、串口数据丢失时如何处理 |
| 恢复 | 故障消失后能否恢复 |
| 日志 | 是否能从日志还原过程 |
| 性能 | 耗时是否超过运行周期 |

## 16. 每次开发的固定工作流

### 开发前

```powershell
& $PYTHON -m unittest discover -s tests -v
& $PYTHON -m tools.离线评测 --output logs\before_change.json
```

### 开发中

- 一次只修改一个问题。
- 每次只改变一个关键参数。
- 先写失败测试，再写实现。
- 关键代码写注释，说明原因而不是重复代码含义。
- 不删除失败测试来让测试通过。

### 开发后

```powershell
& $PYTHON -m unittest discover -s tests -v
& $PYTHON -m tools.离线评测 --output logs\after_change.json
& $PYTHON -m compileall -q app mission protocol vision tools tests
```

最后比较 `before_change.json` 和 `after_change.json`，确认没有让其他场景变差。

## 18. 14 天树莓派前置开发计划

每天最多投入 2 小时。14 天后的目标是形成一个可以迁移到树莓派运行的基本视觉模块：能够读取图像、识别颜色目标和 AprilTag 工位、解析任务扫码、驱动任务状态机、输出 STM32 协议动作、处理传感器安全条件，并生成日志和评测报告。

这里的“基本实现所有任务”指软件功能闭环和接口已经完成，不代表真实场地精度、真实串口稳定性和机械抓取效果已经验证。9 月与控制部分同学联调时，重点是替换真实设备适配器、标定参数和协议时序，不再重写核心流程。

本计划默认你会在 14 天内采购到树莓派，因此第 13～14 天必须安排树莓派实际部署和运行验证。如果摄像头、扫码器、STM32 或传感器也同时到位，就在这两天进行单设备验证；如果只有树莓派到位，则先验证树莓派系统、Python 环境、CPU/内存占用、日志、模拟任务和启动服务。

### 每天固定工作节奏

```text
10 分钟：阅读当天目标和已有代码
70 分钟：实际开发、调试或参数实验
30 分钟：运行测试并查看日志
10 分钟：记录问题、整理文件和备份
```

每天结束必须执行：

```powershell
& $PYTHON -m unittest discover -s tests -q
```

如果测试失败，第二天优先修复失败，不要继续叠加新功能。

| 调试代码 | 在行号左侧设置断点，按 `F5` 启动调试 |

VSCode 操作步骤：

1. 打开项目根目录。
2. 按 `Ctrl+Shift+P`。
3. 输入 `Tasks: Run Task`。
4. 选择需要执行的任务。
5. 在底部终端查看结果。

调试时使用左侧“运行和调试”面板，可以选择：

- `Application Simulation`：调试完整模拟任务。
- `Offline Evaluation`：调试故障场景。
- `Current Python File`：调试当前打开的 Python 文件。

以下操作不能只依靠 Windows 版 VSCode 按钮完成，必须在树莓派的 VSCode Remote SSH 终端或 SSH 终端中执行：

也就是说：开发、测试和模拟可以全部在 VSCode 中完成；树莓派系统安装、GPIO/USB 设备访问和 systemd 服务管理必须在树莓派环境中执行。
