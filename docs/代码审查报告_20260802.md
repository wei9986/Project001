## 二、P0 —— 阻塞性问题（必须先解决）

### P0-1 运行环境损坏：numpy 段错误，所有视觉代码无法运行

**位置**：`.venv/`（`视觉模块开发/.venv`）、`pyvenv.cfg`、`requirements.txt`

**实测证据**（2026-08-02）：
```
import numpy  →  Windows fatal exception: access violation（段错误，exit=139）
import cv2    →  同样段错误
D:\Anaconda\python.exe import numpy → 同样段错误（连 Anaconda base 都崩）
```

**根因链**：
1. `pyvenv.cfg` 中 `include-system-site-packages = true`，venv 创建时挂在 `D:\Anaconda` 之上；
2. venv 自身 site-packages 中**没有安装 numpy**（只有 cv2/opencv-contrib 5.0.0.93、pyserial），`import numpy` 被解析到 `D:\Anaconda\Lib\site-packages\numpy`（numpy 2.3.5）；
3. 该 Anaconda numpy 在当前 Python 3.13.9 环境下加载即触发 access violation —— 这属于**环境级损坏**（连 Anaconda base python 都复现），可能是 numpy 二进制与 Python 3.13.9 ABI 不匹配，或 Anaconda 环境本身损坏；
4. 结果：`vision/颜色追踪.py`、`mission/扫码读取.py`、`tools/仿真验证.py` 等所有依赖 numpy/cv2 的模块**全部无法导入**，现有 34 项单测在当前环境一个都跑不起来。

**影响**：阻塞一切开发、测试、验证与实机联调。昨天（8/1）"34 项测试 OK / 0.418s"的记录与今天矛盾——测试输出甚至可能不是当前环境产生的，**必须重建环境后重新回归验证**。

**建议（修复方向，不在本次执行）**：
- 删除并重建独立 venv（不加 `--system-site-packages`），用 `pip install -r requirements.txt` 安装全部依赖（numpy、opencv-contrib-python、pyserial、ultralytics、Pillow、PySide6）；
- 如果继续使用 Anaconda 的 python.exe 建 venv，需先确认 base 环境 `import numpy` 正常，否则换用官方 python.org 的 3.13.x；
- 在 `docs/无硬件待办.md` 记录重建后的依赖锁（可 `pip freeze > requirements.lock`）。

### P0-2 实机运行循环未接入安全监控，ToF/限位/抓取确认无效

**位置**：`app/实机运行.py`（`LiveRuntime`）vs `app/安全监控.py`（`SafetyMonitor`）

- 仿真路径 `app/运行循环.py` 在动作执行前会调用 `SafetyMonitor.check()`（ToF 距离、限位、装配前抓取确认）——这是对的；
- 但**实机路径 `LiveRuntime.step()` 完全没有调用 `SafetyMonitor`**：`live_config` 里虽然解析了 `safety.minimum_tof_mm`（实机配置.json 中为 80.0），但这个值只被写进 telemetry 日志，**从未用于任何安全判断**；
- `VirtualSensors` 只在仿真里用，实机没有真实 ToF/限位/抓取确认传感器适配器，`SafetyMonitor` 的检查对象缺失。

**影响**：实机运行时，机器人可能在任何距离下执行"取/放/装配"，限位触发也不会阻止动作。方案文档（方案B）明确要求"每个作业工位以视觉/码/ToF 二次校正"、"急停判断"，当前实机路径不满足。

**建议（修复方向）**：为实机实现传感器适配器（ToF、限位、抓取确认），并在 `LiveRuntime._execute()` 下发动作前接入 `SafetyMonitor.check()`，失败时进入恢复流程。

## 三、P1 —— 严重问题（应在联调前修复）

### P1-1 无效扫码会导致任务直接崩溃，而非重试

**位置**：`app/运行循环.py:136`、`app/实机运行.py:284-285`、`mission/任务状态机.py:76`、`mission/扫码读取.py:97-121`

- `ScanResult.valid=False`（空扫、非法字符、JSON 解析失败）时，状态机收到 `task_scanned` 会直接调用 `parse_task_qr()`，其内部对无效结果 `raise ValueError`；
- 该异常在 `RuntimeLoop.step()` / `LiveRuntime.step()` 中没有被捕获：仿真路径会向上抛到 `run()` 直接崩溃；实机路径被 `step()` 顶层的 `except Exception` 吞掉后**任务停留在 S1 但扫码器数据已消费**，无法重试同一张码；
- 离线评测 `tools/离线评测.py:81-86` 里 `invalid_scan` 场景靠 `except (ValueError, KeyError)` 兜底通过，**掩盖了真实路径没有重试机制**的问题。

**影响**：比赛中扫到脏码/反光码即任务失败，与方案文档"S1 读任务失败重试 3 次"不符。

### P1-2 未配置的 AprilTag 也会触发状态推进

**位置**：`app/运行循环.py:140-141`、`vision/站点定位.py:130-156`

```python
station_ready = bool(stations)   # 任意可见标签都算"站点就绪"
```

- `AprilTagStationDetector.detect()` 返回**全部**可见标签，包括 `station_mapping` 中未配置的 tag（`station_id=None`）；
- 运行循环只判断 `bool(stations)`，**没有校验 station_id 是否匹配当前工位**；
- 现场只要出现任何一张无关 AprilTag（甚至别的队伍的标签），就会满足 `station_ready`，配合 `target_ready` 触发 `material_loaded` 等确认事件，导致状态机在错误位置推进。

**影响**：多队伍同场时极易误触发；与方案"站点识别 + 二次校正"目标不符。

### P1-3 `ring_code` 全局唯一校验与赛题语义冲突

**位置**：`mission/任务计划.py:81-83`

```python
self.ring_codes = {item.ring_code for item in (*first, *second)}
if len(self.ring_codes) != len(first) + len(second):
    raise ValueError("任务二维码中存在重复 ring_code")
```

- 赛题中红/绿/蓝三色环分别对应 1/2/3，**两批物料完全可能使用相同色环码**（例如第一批放红色环、第二批装配的物料也是红色系）；
- 当前校验强制**所有物料 ring_code 全局互异**，一旦任务码里两批出现相同环码，`TaskPlan` 构造即抛异常，任务无法开始；
- 仿真任务.json 恰好避开了这个情况（F1红/1、F2绿/2、S1蓝/3），测试也因此通过，掩盖了真实任务码会触发的问题。

### P1-4 协议动作映射三处不一致

**位置**：`protocol/串口协议.py:185-199`（send_action）、`protocol/协议仿真.py:53-62`（ProtocolActionBridge.ACTION_TYPES）、`app/实机运行.py:24-33`（ACTION_TYPES）

| 动作 | 实机运行.py | 协议仿真.py | 串口协议.py send_action |
|---|---|---|---|
| load_first/second_material | **PICK (0x24)** | APPROACH_TARGET (0x10) | 无此动作名 |
| grasp | 无 | 无 | GRASP (0x12) |
| approach_target | 无 | 无 | APPROACH_TARGET |

- 三套映射表各自独立、命名不统一（`load_first_material` vs `grasp` vs `place_target`），同一个业务动作在仿真和实机中发出**不同命令码**；
- 实机用的 `PICK` 而仿真用的 `APPROACH_TARGET`，意味着**仿真通过的协议闭环在实机上行为不一致**，且 F407 固件尚未定义 `PICK` 的具体语义；
- `protocol/串口协议.py` 的 `send_action` 与 `app/实机运行.py` 的 `ACTION_TYPES` 功能重复，维护时容易漂移。

### P1-5 实机配置与方案参数不一致（波特率、心跳、超时）

**位置**：`config/实机配置.json` vs 方案文档 / `protocol/串口协议.py` 默认值

| 参数 | 实机配置.json | 方案B文档 | 串口协议默认 |
|---|---|---|---|
| controller 波特率 | 115200 | 921600 bps UART | 115200 |
| scanner 模式 | camera_qr | GM865 独立扫码器（serial） | — |
| 心跳间隔 | 100ms | 100ms | 100ms |
| 离线判定 | 1000ms | 500ms 判定离线 | 1000ms |
| ACK 超时 | 1500ms | 5s 重试 1 次 | 5000ms |

- 波特率与方案不符（115200 vs 921600），且与初赛源码（9600bps）也完全不同——**协议三层参数目前没有对齐的权威来源**；
- `scanner.mode` 默认 `camera_qr`，但方案明确要用 GM865 串口扫码器，实机联调时若沿用默认配置会走错扫码路径。

### P1-6 `视觉应用.py` 异常路径引用未定义变量

**位置**：`app/视觉应用.py:171-179`（main 的 live 分支）

```python
except Exception as exc:
    session.write("fatal_error", {...})
    raise
finally:
    session.close(runtime.machine.state.value, { ... runtime.controller.reconnects ... })
```

- `runtime` 变量在 `try` 块**之前**由 `runtime = LiveRuntime(...)` 赋值（第 166 行）；
- 如果 `LiveRuntime.__init__` 本身抛异常（例如相机/串口/配置问题），`session` 已创建、`runtime` 未定义，`finally` 中访问 `runtime.machine` 会抛 `UnboundLocalError`，**掩盖原始错误**；
- 审查确认：`LiveRuntime.__init__` 中确实存在多条可抛异常的路径（`load_config`、`AprilTagStationDetector.from_config`、`CameraCalibration.from_file` 等），此问题概率不低。

### P1-7 精定位/视觉任务状态机存在死锁路径

**位置**：`mission/视觉任务状态机.py:93-100`、`vision/精定位.py:160-190`

- `FINE_LOCALIZING` 状态依赖 `world_mm`（精定位坐标），而 `world_mm` 只有完成相机平面标定（`calibration` 非空）才会产生；
- `config/实机配置.json` 中 `"calibration": null`——**当前配置下 `FineLocalizer` 永远拿不到 world_mm，会一直返回 NO_COORDINATE**；
- `TaskStateMachine` 对 `NO_COORDINATE` 没有分支处理（只处理 STABLE/TIMEOUT/LOST/JUMP_REJECTED），返回空动作列表 → 状态机停在 FINE_LOCALIZING 直到超时 → 恢复 → 重新搜索 → 再进入 FINE_LOCALIZING → 无限循环，直到 `max_recovery_attempts` 耗尽。

**影响**：未标定相机时视觉任务状态机必然耗尽恢复次数失败。这不是测试能覆盖的路径（仿真里 `run_state_machine_simulation` 用了带 world_mm 的假目标），实机一旦沿用默认配置就会踩中。

### P1-8 `仿真验证.py` / `离线评测.py` 的默认输出目录被 .gitignore 忽略

**位置**：`tools/仿真验证.py:247`（`runs/simulation_validation.json`）、`tools/离线评测.py:106`（`logs/offline_evaluation.json`）

- `.gitignore` 忽略了 `runs/` 和 `logs/`，这两类报告**不入版本管理**；
- 但项目说明/进度文档要求"测试报告和日志路径"提交验证——矛盾。验证结果（通过/失败、指标）一旦被本地覆盖即丢失，无法追溯"什么时候、什么配置下通过"。

## 四、P2 —— 一般问题（值得修复）

### P2-1 心跳与命令共用序号空间，可能相互干扰

**位置**：`protocol/串口协议.py:163-167`、`225-226`

- `_allocate_sequence()` 同时为命令和心跳分配序号，心跳也会占用序号；
- 若心跳序号与未完成命令的序号相同（序号 1..255 循环后），F407 回的心跳应答可能被 `receive()` 误匹配到 pending 命令；
- 当前测试未覆盖"心跳序号与命令序号碰撞"场景。

### P2-2 `FrameParser` 对错误帧的丢弃粒度过大

**位置**：`protocol/串口协议.py:101-115`

- CRC/版本/类型校验失败时 `del self.buffer[:2]`（丢弃帧头 2 字节），若坏帧中间恰好含 `0xAA 0x55`，会导致后续有效帧被误吞或偏移解析；
- 对 `message_type` 未知的帧，丢弃 `total_length` 字节——但此时 payload_length 可能已不可信，跳过量可能越过真实帧边界。

### P2-3 未配置 AprilTag 字典名校验缺 OpenCV 版本兜底

**位置**：`vision/站点定位.py:90-107`

- `getattr(cv2.aruco, dictionary_name)` 对 OpenCV 5.x 的新 API 与旧版 API 分支都做了处理，但 `DetectorParameters_create()` 旧路径在 OpenCV 4.7+ 已移除——旧路径实际不可用；
- 若部署的 OpenCV 版本 < 4.7（树莓派 apt 安装的默认版本可能较旧），`ArucoDetector` 分支不成立、`DetectorParameters_create` 又不存在，构造即失败。

### P2-4 颜色追踪的超时控制与 ROI 存在不一致

**位置**：`vision/颜色追踪.py:432-440`

- `timeout_ms` 检查是在**每个颜色循环内部**累计 `elapsed_ms` 后判断，颜色数多时前面的颜色可能已超时，后面的颜色直接返回 `timeout` 空结果；
- 但 `_empty_result("timeout")` 的 `rejected_count` 恒为 0，且 `timed_out` 标记在结果里是 per-color 的，上层 `RuntimeLoop` 只取 `targets`，不感知部分颜色超时——**静默丢颜色**。

### P2-5 `run()` 超时抛 `TimeoutError` 而非进入恢复

**位置**：`app/运行循环.py:186-190`

- 仿真/离线评测中 `run()` 超时直接 `raise TimeoutError`，而状态机本身有 `tick()` 恢复机制；
- 二者语义重叠且不一致：`tick()` 说"超时进恢复"，`run()` 说"超时即失败"。测试里 `target_lost`/`apriltag_lost` 场景期望的是 `timeout`（抛异常），说明当前设计把"超时"当作失败结果而非可恢复事件。

### P2-6 `ActionLogger` / `RuntimeSnapshotLogger` 每次写日志都重新打开文件

**位置**：`app/视觉应用.py:46-47`、`app/运行观测.py:22-23`

- 每帧/每个动作 `open(path, "a")` 一次，实机 30fps 下每秒数十次 open/close 系统调用；
- 与 `DetectionLogger`（持有文件句柄 + flush）的实现不一致，实机上会带来不必要的 IO 开销和日志丢失风险（异常时缓冲区未落盘）。

### P2-7 配置文件校验不完整

**位置**：`tools/启动检查.py`

- `REQUIRED_FILES` 列了 6 个 JSON，但校验器 `VALIDATORS` 只覆盖 4 个（缺 `任务配置.json`、`仿真任务.json` 的结构校验）；
- `任务配置.json` 的 `barcode_mapping`/`stations` 内容不校验，当前文件里全是 0/占位值，启动检查通过但**坐标未实测**，实机会用假坐标跑。

### P2-8 测试盲区

**位置**：`tests/`

- 无 `LiveRuntime` 端到端测试（相机/扫码/协议/状态机串联只测了仿真版）；
- 无 `SafetyMonitor` 在 `LiveRuntime` 路径的测试（P0-2 的佐证）；
- 无"任务码含重复 ring_code"的测试（P1-3 的佐证）；
- 无无效扫码重试测试（P1-1 的佐证）；
- 无未配置 tag 触发推进的测试（P1-2 的佐证）；
- 无心跳序号碰撞测试（P2-1 的佐证）。

### P2-9 `实机运行.py` 中 `_archive_error_frame` 的取模逻辑

**位置**：`app/实机运行.py:214-226`

- `self.error_frame_index % max(interval, 1)` 恒等于 0（`error_frame_index` 从 1 开始递增，interval 默认 30，1%30=1≠0……实际是**每帧判断余数**，只有 index 为 30/60/90… 时余数为 0 才保存）——逻辑正确但 `max(interval, 1)` 使 interval=0 时每帧保存，注释说"避免淹没磁盘"却允许 0 值，语义矛盾。

### P2-10 `TestSession.close()` 的 `scan_success_rate` 除零

**位置**：`app/测试会话.py:62-63`

- `self.counts["scans"]` 为 0 时用三元表达式返回 `None`——已处理，但 `average_fps` 用 `frames/duration_s`，duration_s 若极小会有夸张值；属健壮性小问题。

### P2-11 `PiTelemetry` 在 Windows 下每次调用都跑 `vcgencmd`

**位置**：`app/实机设备.py:190-195`

- 非树莓派（Windows 开发机）下每次 `snapshot()` 都执行 `subprocess.check_output(["vcgencmd", ...])`，`FileNotFoundError` 被捕获但**每次都有子进程启动开销**；且捕获了 `FileNotFoundError`/`CalledProcessError`，但 `OSError`（如权限）未捕获。

### P2-12 文档/代码不一致

**位置**：`项目说明.md`、`docs/`、代码 docstring

- `项目说明.md` 列出 `config/` 无 `精定位配置.json`，但实际文件存在且被多处引用——文档滞后；
- `docs/无硬件待办.md` 记录"28 项测试通过"，实际测试文件已有 6 个测试类（34 项），文档数字滞后。

## 六、交叉验证结论（配置 × 代码 × 方案）

1. **协议参数无权威来源**：实机配置（115200 / 1500ms / 1000ms）≠ 方案B（921600 / 5s / 500ms）≠ 协议默认（115200 / 5000ms / 1000ms）≠ 初赛源码（9600 / FF-FE 帧）。实机联调前必须冻结一套，建议以方案文档为准。
2. **仿真与实机行为割裂**：仿真路径（运行循环 + SafetyMonitor + VirtualSensors）与实机路径（LiveRuntime，无安全监控、无传感器）是两套几乎不共享逻辑的实现，仿真通过≠实机可靠。
3. **安全设计缺口**：方案强调"通信心跳停车、限位、ToF 二次校正、抓取确认"，实机路径一个都没有落地——这是从"能跑通仿真"到"能上场比赛"的最大鸿沟。
4. **任务状态机（S0-S5）vs 视觉任务状态机（搜索-抓取-放置）是两套独立状态机**：`MissionStateMachine`（两批物料流程）与 `TaskStateMachine`（单目标抓放）互不引用，`LiveRuntime` 只用了前者，后者只被仿真验证覆盖——**实机任务流程缺少"搜索→精定位→抓取→放置"的完整闭环**，这是方案"视觉二次校正"落地的关键缺口。
