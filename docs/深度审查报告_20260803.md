## 二、P0 —— 阻塞性问题（必须修复）

### P0-1 恢复机制整体失效：恢复成功后不重发被中断的动作，任务最终必然 FAILED
- **位置**：[app/实机运行.py:201-208](app/实机运行.py#L201-L208)、[app/运行循环.py:144-157](app/运行循环.py#L144-L157)、[mission/任务状态机.py:127-129](mission/任务状态机.py#L127-L129)
- **描述**：任何 `safety_fault` / `communication_lost` / 状态超时都会让状态机进入 RECOVERY 并产出 `recover`。恢复成功 `recovery_done` 只让状态机回到 `resume_state` 并输出一个**无串口命令、无确认事件映射**的 `resume_state` 动作（`ACTION_TYPES` 与 `DONE_EVENTS`/`ACTION_EVENTS` 中均无此动作）。被中断的动作（被安全门拦下的 `load_first_material`、写失败丢掉的 `place_ring`）**永远不会被重新下发**，状态机停在 resume_state 等一个永远不来的确认事件 → `tick()` 超时 → 再次恢复 → 次数耗尽 → `safe_stop` → **FAILED**。仿真与实机两条路径都走同一死局。
- **触发场景**：实机任何一次恢复成功之后；或仿真触发安全故障/状态超时后。
- **影响**：整个异常恢复/安全停车功能形同虚设。叠加 P0-2，实机跑标准两批任务必然 FAILED。

### P0-2 实机安全传感器是静态占位，`assemble_material` 在实机路径恒被安全门拦截
- **位置**：[app/实机运行.py:109](app/实机运行.py#L109)、[app/实机设备.py:189-196](app/实机设备.py#L189-L196)、[app/安全监控.py:37](app/安全监控.py#L37)、[config/实机配置.json:35-39](config/实机配置.json#L35-L39)
- **描述**：`LiveSensors` 只在 `LiveRuntime.__init__` 由 `from_config` 一次性初始化，**全仓库 grep 确认没有任何代码在运行时更新 `grasp_confirmed`**（不解析 F407 报文、不读 GPIO）。`实机配置.json` 中 `grasp_confirmed: false` 是静态值，因此 `SafetyMonitor.check("assemble_material")` 恒返回 `grasp_not_confirmed` → `_execute` 抛 `safety_fault` → 恢复 → 最终 FAILED。同理 `tof_distance_mm: null` 使 ToF 检查整体跳过、`limit_triggered: false` 使限位检查失效——实机侧安全门要么对大多数动作完全失效，要么对装配动作一票否决。
- **触发场景**：实机模式、任务码含 `second_batch`（标准赛题两批物料），运行到 S4 装配即被永久拦截。

## 三、P1 —— 严重问题（实机联调前应修复）

### P1-1 串口写失败后 pending 悬挂，recover / safe_stop 无法下发
- **位置**：[app/实机运行.py:169-178](app/实机运行.py#L169-L178)、[protocol/串口协议.py:219-220](protocol/串口协议.py#L219-L220)、[app/实机设备.py:135-140](app/实机设备.py#L135-L140)
- **描述**：`send_command` 在 [串口协议.py:223](protocol/串口协议.py#L223) **先创建 pending**，随后 `controller.write` 才执行。写失败（串口未打开/短写）后 pending 保持「未完成未失败」，[串口协议.py:219](protocol/串口协议.py#L219) 拒绝后续所有 `send_command` → recover 无法下发 → 循环到 FAILED；`safe_stop` 因 pending 阻塞走 `continue` 被跳过，**F407 收不到任何停止指令**。且 `poll()` 会在串口恢复后重发该悬挂命令，F407 可能执行一个 Pi 已放弃的动作，两侧状态失步。
- **触发场景**：F407 未上电启动 / 比赛中拔线 / 921600 高波特率短写——启动联调最常见路径。
- **修复方向**：写失败时立即把 pending 置为 failed（或回滚），再进入 `communication_lost`。

### P1-2 恢复态再次失败会把 `resume_state` 覆盖为 RECOVERY 自身，永久卡死
- **位置**：[mission/任务状态机.py:159-169](mission/任务状态机.py#L159-L169)、[mission/任务状态机.py:173](mission/任务状态机.py#L173)
- **描述**：`_recover` 无条件 `resume_state = self.state`。若失败事件在机器已处于 RECOVERY 时再次到来（如 F407 对 RECOVER 判 FAIL 后重试成功），`resume_state` 被覆盖为 RECOVERY；恢复成功后跳回 RECOVERY 并输出无映射的 `resume_state` 动作，而任务级 `tick()` 显式排除 RECOVERY 不做超时 → **永久停在 RECOVERY**，只能靠 `max_cycles`/`max_runtime_s` 兜底。
- **触发场景**：RECOVER 命令第一次被 F407 判 FAIL、重试第二次才成功。

### P1-3 `ack_timeout` 同时充当 DONE 超时，动作执行慢会重复下发同一命令
- **位置**：[protocol/串口协议.py:223](protocol/串口协议.py#L223)、[protocol/串口协议.py:257-261](protocol/串口协议.py#L257-L261)
- **描述**：`deadline_ms` 只在 `send_command`/重试时设置，**收到 ACK 后不重置**。`poll` 判定 `not completed and now >= deadline`——ACK 后 `acknowledged=True` 但 `completed=False`，动作执行超过 `ack_timeout_ms`（实机配置 5000ms）就会向 F407 重发同序号命令。同理 DONE 到达但 ACK 丢失时（`protocol_done_without_ack`，[行 241-245](protocol/串口协议.py#L241-L245)）也会重发一条 F407 已执行完的命令。**若 F407 不按序号去重，抓取/装配会被物理重复执行**（需验证 F407 固件）。
- **触发场景**：任何物理动作耗时 > 5s（抓取/装配/回零都可能数秒级）。

### P1-4 相机断连期间 `machine.tick()` 被跳过，状态超时恢复被禁用
- **位置**：[app/实机运行.py:265-269](app/实机运行.py#L265-L269)
- **描述**：`step()` 在相机读不到帧时直接 `record_frame(dropped) + return`，**跳过了末尾的 `tick()`**。而 `tick()` 是唯一的状态级超时→恢复触发点。相机持续失败时，处于「等待视觉确认才能推进」的状态（如 `place_ring` 等站点可见）既无法推进也无法超时恢复，只刷 `camera_error`，直到 `max_runtime_s` 兜底。
- **触发场景**：比赛现场相机松动 / USB 掉线数秒以上。

### P1-5 颜色匹配算法组合爆炸，默认配置下贪心兜底不可达
- **位置**：[vision/颜色追踪.py:525-546](vision/颜色追踪.py#L525-L546)、[vision/颜色追踪.py:467](vision/颜色追踪.py#L467)
- **描述**：`_best_track_matches` 用 `itertools.combinations` × `permutations` 穷举，切贪心的守卫要求 `min(candidate_count, track_count) > 8`；而候选已被 `max_targets_per_color=8`（[行 467](vision/颜色追踪.py#L467)）截断，**candidate_count 恒 ≤8，贪心分支在默认配置下不可达**。实测 8×8 全不命中 **~496ms/帧**，远超 `timeout_ms=50` 预算 → 该颜色超时，后续颜色（green/blue）每帧被 `_mark_color_timed_out`，轨迹反复丢失无法确认。树莓派上更严重。
- **触发场景**：一个颜色出现 7~8 个候选（料区多个同色物料块）。

### P1-6 外接扫码器 128 字节上限装不下任务二维码
- **位置**：[mission/扫码读取.py:33](mission/扫码读取.py#L33)、[mission/扫码读取.py:45-52](mission/扫码读取.py#L45-L52)、[config/实机配置.json:10-14](config/实机配置.json#L10-L14)
- **描述**：`ExternalScannerParser.max_line_length=128`，超长整行判「扫码数据过长」；分包到达且缓冲超 128 字节无 `\n` 则清缓冲判「缓冲区溢出」。而任务二维码 JSON 序列化后约 210+ 字节。实机配置默认 `scanner.mode=serial`、`scan_type=task_qr` → **任务码经该解析器必然判无效** → S1 重试耗尽 → 失败。`camera_qr` 模式不受影响。
- **触发场景**：GM865 串口扫码器读取任务二维码（实机默认路径）。需验证实际比赛是否改用相机读任务码。

### P1-7 心跳离线检测（`is_online`/`offline_timeout_ms`）未接入实机循环
- **位置**：[protocol/串口协议.py:210-213](protocol/串口协议.py#L210-L213)、[app/实机运行.py:184-208](app/实机运行.py#L184-L208)
- **描述**：`is_online()` 定义完好，但**全项目仅测试调用**；`offline_timeout_ms: 1000` 只被读入配置从未使用。F407 静默死机/断电时，若当前无 pending 命令，Pi 持续发心跳、读空缓冲，既不推进也不恢复，直到下一次动作才被 `ack_timeout`(5s) 间接捕获。「心跳停车」安全功能未落地。
- **触发场景**：F407 在任务间隙（无待完成命令）断电或固件挂死。

### P1-8 精定位/视觉任务状态机整条链路未接入实机，「视觉二次校正」缺失
- **位置**：[app/实机运行.py:134-140](app/实机运行.py#L134-L140)、[mission/视觉任务状态机.py](mission/视觉任务状态机.py)（整体）、[app/实机运行.py:97-103](app/实机运行.py#L97-L103)
- **描述**：`FineLocalizer`/`TaskStateMachine` 只在 `tools/仿真验证.py` 与 tests 中使用；`LiveRuntime.step()` 只驱动 S0-S5 任务状态机，`search_target`/`approach_target`/`grasp`/`place_target` 等视觉级动作在 `ACTION_TYPES` 有映射但**没有任何产生者**。`create_fine_localizer` 全项目无调用点，`精定位配置.json` 被加载但从不消费。方案要求的「搜索→精定位→抓取→放置」闭环在实机不落地。
- **触发场景**：实机部署时，抓取前无精定位稳定确认流程。

### P1-9 视觉任务状态机：`calibration=null` 时永远卡在 SEARCHING；JUMP_REJECTED 被当终止失败
- **位置**：[mission/视觉任务状态机.py:61-65](mission/视觉任务状态机.py#L61-L65)、[mission/视觉任务状态机.py:98-105](mission/视觉任务状态机.py#L98-L105)、[vision/精定位.py:207-211](vision/精定位.py#L207-L211)、[config/实机配置.json:31](config/实机配置.json#L31)

### P1-10 Qt 调参切换颜色时静默覆盖新颜色的 HSV 配置（可污染落盘）

## 四、P2 —— 一般问题

### 状态机 / 运行时
- **P2-1 tick 超时与在途命令冲突，recover 被误判为 communication_lost**：[app/实机运行.py:303-304](app/实机运行.py#L303-L304) + [protocol/串口协议.py:219-220](protocol/串口协议.py#L219-L220)。`ack_timeout_ms`(5000) 与 `state_timeout_ms`(5000) 相等，命令跑满 5s 未 DONE 时 tick 产出 recover 被「已有未完成指令」拒绝 → 误判 communication_lost → 白白消耗恢复次数，RECOVER 从未真正下发。
- **P2-2 相机断连/视觉异常被吞，持久性错误导致任务停滞**：[app/实机运行.py:270-276](app/实机运行.py#L270-L276)。`tracker.track()`/`station_detector.detect()` 异常被 try/except 吞掉只写 `vision_error`；若异常是持久性的（如标定分辨率与相机实际输出不符，`undistort` 每帧抛错），每帧都被丢弃、任务永远无法推进、只留海量同一条错误日志。
- **P2-3 超过 `max_lost_frames` 的轨迹被静默移除，最终丢失事件丢失**：[vision/颜色追踪.py:503-514](vision/颜色追踪.py#L503-L514)。丢弃判断是 `lost_frames <= max_lost`（第 513 行），超限轨迹直接从 `self.tracks` 移除，`lost_targets` 不再包含它——「目标最终丢失」没有任何结果输出，下游按 target_id 关联的消费者感知不到。
- **P2-4 `scan_retries` 恢复后不重置，S1 恢复后不再有重试配额**：[mission/任务状态机.py:91-95](mission/任务状态机.py#L91-L95)。只有解析成功时才清零；恢复回 S1 后下一次无效扫码立即 `>= max_scan_retries` 再次触发恢复。
- **P2-5 重复确认事件导致 `plan.update` 抛 ValueError 崩溃**：[mission/任务状态机.py:99-102](mission/任务状态机.py#L99-L102)、[mission/任务计划.py:101-109](mission/任务计划.py#L101-L109)。状态机不幂等，重复 `material_loaded`/`assembly_done`（如 F407 重复回 DONE、缓冲残留旧帧误匹配）会抛 `ValueError`，实机路径无 try 包住状态机调用直接终止整场任务。属防御性缺口（协议按序号匹配基本能阻止，低概率）。
- **P2-6 `任务配置.json` 的 barcode_mapping / stations 是生产死代码，坐标全 0 占位**：[mission/任务计划.py:32-60](mission/任务计划.py#L32-L60)、[mission/扫码读取.py:124-136](mission/扫码读取.py#L124-L136)、[config/任务配置.json](config/任务配置.json)。`TaskRuntimeConfig` 仅测试/启动检查消费，`BarcodeWorldMapper` 全项目无调用，坐标全 0 占位即便被读也会用假坐标跑。
- **P2-7 `ring_code` 未校验取值域 1/2/3**：[mission/任务计划.py:83-87](mission/任务计划.py#L83-L87)。注释声明「1/2/3 对应红/绿/蓝」，但校验只要求批次内唯一；`ring_code="9"` 或空串也能通过并进入流程。

## 七、交叉验证结论（配置 × 代码 × 方案）

1. **恢复机制是全项目最大架构缺口**（P0-1 + P1-1 + P1-2 + P2-1 同根）：`recover` 动作要么因 pending 悬挂发不出去，要么恢复成功后不重发被中断动作。异常恢复与安全停车目前只是「状态图」而非「能力」。
2. **实机安全传感器是占位**（P0-2）：`LiveSensors` 无运行时数据源，ToF/限位/抓取确认全部悬空；而 `SafetyMonitor` 又对 `assemble_material` 一票否决——实机安全门「该拦的拦不住、不该拦的必拦」。
3. **视觉二次校正未落地**（P1-8 + P1-9）：精定位/视觉任务状态机只存在于仿真与测试，实机 S0-S5 流程直接下 PICK/ASSEMBLE 给 F407，与方案「视觉/码/ToF 二次校正」要求不符。
4. **仿真与实机行为割裂**（P2-10/P2-11/P2-12/P3-13）：安全默认值相反、异常处理相反、视觉超时预算差 20 倍、协议发送机制三入口并存——仿真通过不能作为实机可靠的依据。
5. **协议超时语义需按 F407 固件冻结**（P1-3）：ACK 与 DONE 共用 deadline 是否造成重复执行，取决于 F407 是否按序号去重，联调前必须确认并收敛一套权威参数。

## 八、建议修复优先级

1. **立即**：P0-1 恢复后重发被中断动作（或改语义为「恢复即重新下发当前动作」）、P0-2 实机 `grasp_confirmed` 注入真实数据源（F407 遥测/GPIO，未接前应放行而非一票否决）。
2. **实机联调前**：P1-1 写失败回滚 pending、P1-2 恢复态自保护、P1-3 拆分 ACK/DONE 超时、P1-4 相机断连仍 tick、P1-6 扫码器长度与任务码对齐、P1-7 心跳离线接线、P1-8/P1-9 精定位链路接入或明确拆分、P1-5 匹配算法限幅。
3. **联调后**：P2 各项（状态机幂等、配置校验补全、仿真 gate 补全、Qt 调参防护）。
4. **长期**：仿真/实机共享同一套动作执行 + 安全 + 传感器接口，P3 规范化。
